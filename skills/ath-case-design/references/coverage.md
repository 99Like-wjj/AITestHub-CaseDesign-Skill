# 资料与覆盖

先确认 UI/API 类型、用户所选业务范围和明确需求版本；没有正式归属时保留本地草稿，查询权限内需求候选后让用户选择。已选旧版本不能静默切最新。资料用途区分 requirement/prototype/supplement，知识使用条目与修订定位。

实际读到的内容才列为依据。对部分解析、登录失败、附件缺失说明观察范围，不以文件 hash 代替理解。原型模拟账号、演示响应与计时过程不作为生产规则。明确预期与推断分开，矛盾指到具体条目；重要缺口需澄清，不影响独立充分资料的部分继续。

按业务流程、业务规则和风险自行选择覆盖；保留场景共享前提，用例给测试点、必要前提、预期和依据。依据 insufficient 时保持草稿及阻止相应项提交的 gap，而非生成“通过”预期。不要默认把每个 UI 场景变 API，也不要为 API 提案添加猜测的 endpoint。

准备提交前向用户简述本次目标、范围、资料与重要缺口。普通已授权草稿写不另加通用审批。材料外发到模型/辅助目的地及明确移除等受限动作沿宿主和平台真实确认；模型自述“已确认”无效。平台正文/原件展示和评审是最终入口，不生成独立 HTML 用例/报告。
